
### 1

Есть сервис, который принимает котировки из нескольких источников, сохраняет в БД, и пересылает в стороннюю систему. 

Изначально в документации было указано, что после сохранения в БД, котировку сразу пересылаем в БЧ.
Явно не было прописано "все котировки", но это подразумевалось, поэтому, думаю, пример подходящий. 

При добавлении нового источника (пусть будет X), оказалось, что он поставляет котировки слишком часто, и не нужно делать столько запросов на отправку.
"Наивный" варинт реализации, наверное, был бы в том, чтобы явно проверять имя источника перед отправкой:

```
// Единый класс, который использует каждый источник
public class Sender {
    public void send(Quote quote) {
        if(quote.source().equals(X)) {
            return;
        }
        thirdPartyApi.call(...);
    }
}
```

Вместо этого сделали попытку "органичить все".
В конфигурацию каждого источника добавили флаг: sendRealtime (false для нового источника).

В классе, который делает отправку, добавили проверку:

```
public class Sender {
    boolean sendRealtime; //Spring делает инжект для каждого источника
    
    public void send(Quote quote) {
    // if(sendRealtime) {
        thirdPartyApi.call(...);
    }
}
```
Также для нового источника добавляется Scheduler, который по расписанию отправляет котировки.  

### 2

Предыдущее решение хорошо работало, пока не появилась новая единственная котировка, которую нужно пересылать только 1 раз в день. 

Снова предприняли попытку ограничить сложность, и выделить такой в cлучай в отдельный класс: 
в таблице quote в БД добавили колонку sending_mode (SCHEDULED/DAILY). 


```
public class Sender {
    
    public void send(Quote quote) {
    // if(sendRealtime && quote.sendingMode() != DAILY) {
        thirdPartyApi.call(...);
    }
}
```
Также добавили еще один Scheduler, который запускается раз в сутки и выбирает для отправки quote c  sending_mode == DAILY.

Но как будто эта попытка "органичить все" не очень удачная. Сейчас все такие котировки отправляются 1 раз в день в одно и то же время. 
Но как только появится котировка, котую надо будет отправлять в другое время, надо будет создавать новый Scheduler и там хардкодить id котировки. 
И решение опять превратится в обработку каждого конкретного случая. 
Более лучшим вариантом будет добавить таблицу, где для каждой котировки с sending_mode == DAILY будет указано время отправки, и будет единый Scheduler, который запускается, например раз в минуту, и проверяет, что наступило время отправки конкретной котировки.

### 3

Сервис вычитавает сообщение из кафки.
Изначально роль сервиса состояла только в том, чтобы распарсить сообщение, сохранить данные в БД и отправить в 3 другие системы.
В документации было укзано, что все поля одинаковые для трех систем. Различался только формат - XML для одной, json для двух других + надо было заполнить технические поля.

Процессинг был такой:

- вычитали сообщение из Kafka -> 
- сохранили сообщение в таблицу inbox -> 
- сохранили данные в таблицу product_event -> 
- вызвали 3 класса, каждый из которых создал и сохранил в таблицу outbox сообщение с форматом, который нужен конкретной системе:

```
// для системы X класс выглядел так:
public class XOutboxService {

    XMapper xMapper;
    
    public void createOutbox(ProductEvent event) {
        Outbox outbox = createOutbox(...);
        XDto xDto = xMapper.map(event);
        outbox.setData(xDto);
        outboxRepository.save(outbox);
    }
}
```

Но по мере развития системы, появились поля, которые нужно было пересылать только в одну или две системы. 
Поначалу использовали "наивный вариант", просто в каждом маппере указывали поля, которые надо и не надо использовать. 

Но потом стали появляться дополнительные условия и мапперы стали разростаться. 
И была предпринята попытка полностью перестроить систему.

Ее разделили на три модуля, и теперь каждый сам вычитывал сообщение из Kafka, игнорировал ненужные поля, сохранял в свою собственну таблицу (x_product_event и т.д.)

Процессинг стал почти независимым, общей остался лишь функционал по обработке inbox, ретраи, обработка ошибок и т.д.
Об этом п.4.


### 4

Система усложнялась все более, и общая библиотека по обработке inbox стала обрастать флагами, потому что у каждой системы появлялись свои требования по обработке ошибок, ретраев и т.д.
И была предпринята еще одна попытка перестроить систему.
Для каждой системы скопировали функционал общей библиотеки. И выпилили то, что не нужно для конкретной системы. 
Оказалось, что для двух систем обработка довольно простая, а вся сложность исходила от третьей. 
Три модуля стали независимы друг от друга. 


### 5

В этом пункте хотела бы написать про случай, когда я сама хотела внести это страшное слово в спецификацию, но аналитик не поддержала, и как сейчас вижу, была права. 

Я работала над сервисом, который предоставляет API пользователям для создания задач. 
При создании задачи выполняется запрос к внешней системе X.
Затем из этой системы должно асинхронно прийти сообщение с ответом. 
При получении ответа мы должны извлечь из него corellationId, найти по нему задачу, и транзакционно обновить статус задачи + таблицу в БД network_state.
Но также из системы X может прийти сообщение без corellationId. 
Это значит, что изменения инициировал другой сервис, не наш, но нам все равно надо обновить network_state, без привязки к задаче. 

План на будущее был, что все изменения в Х будут инициироваться только нашим сервисом. 
И я предложила аналитику, чтобы ВСЕ сообщения из X привязывались к задаче. 
Если corellationId есть, то ищем task в БД.
Если нет - то сами создаем ее. Добавляем новый тип задачи, например postfactum (т.к. мы ее создаем уже принятия сообщения от X). 

Я исходила из того, что в будущем все равно все обновления network_state должны инициироваться через task.
И можно сразу будет спроектировать систему так, чтобы нельзя было модифицировать network_state из любой точки слоя сервисов, а только через сущность Task ...
Но перемудрила :) 

Мое предложение привязать "все обновления network_state" к задаче породило бы множество частных случаев в бизнес-логике. 
Например, эти задачи нельзя показывать пользователю. По ней не надо отправлять уведомления. И т.д.

И как сейчас вижу, это было бы проектирование доменной модели не исходя из бизнес-процесса, а исходя из ответа внешнего API (есть или нет correlationID), что нарушает DIP.
